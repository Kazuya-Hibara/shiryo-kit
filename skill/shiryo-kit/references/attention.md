# attention.md — ずれない仕組み (長い案件・任せる時・再開する時)

## なぜ要るか

資料づくりは長い。途中でモデルは、合意した要件を忘れる・空白をもっともらしく埋める・自分の下書きを自分で甘く点検する・過去資料を読み込みすぎて大事なことが押し出される、という形でずれる。
これを、気をつけることではなく、file と決まった手順で防ぐ。

## 1. 正本は file

会話は正本ではない。次の file が正本で、迷ったらここに戻る。

| file | 正本として持つもの |
|---|---|
| BRIEF.md | 要件・受け手・仮定・未確定・決定ログ・spec_rev |
| ledger.md + sources/ | 主張ごとの確認状態と原典の引用 |
| issues.md | 指摘・未決・新しく分かった事実 |
| versions.md | 版と、検品した版・納品した版の対応 |
| review/ | 検品結果と起動記録 |

## 2. 読み直す時

次の時は、必ず BRIEF.md を読み直してから動く (spec_rev も見る)。

- 骨子を作る前、下書きを始める前
- 台帳を全文から抜き出し直す前
- subagent や別プロセスに頼む前、その返事を使う前
- 検品を頼む前、検品の指摘を直す前
- 修正の指示を受けて直す前
- 中断・再開・会話の要約 (compact) の後 — 最初の動作として
- 納品の報告をする前、メモを保存する前

読み直したら、次の 3 問を自分に当てる:
1. 今やろうとしていることは、BRIEF のどの要件 (B-xx) に当たるか
2. 「言わないこと」や BRIEF の範囲の外に出ていないか
3. BRIEF に無い前提 (推測) を足していないか — 足しているなら、それは仮定か未確定として扱う

## 3. subagent や別プロセスへの依頼文

依頼は案件フォルダの `work/request-<名前>.md` に書き、その path を渡す。要約ではなく、読むべき file の path を渡す。

```markdown
# 依頼 <名前> (spec_rev <n>)
目的: <何のためか 1-2 文>
仕事: <1 つに絞る>
読む物: <file の path>
終わる条件: <ここまでやったら返す>
返す形: 下の「返事の形」
書いてよい場所: <path> (それ以外は書かない)
しないこと: 利用者に質問しない / 成果物を直さない (頼まれた時以外) / 顧問先の個人情報を返事に入れない / 読んだ本文を丸ごと返さない
```

## 4. 返事の形

```markdown
spec_rev: <依頼文の spec_rev をそのまま>
結論: <1-3 行>
根拠: <file の path と場所、引用は短く>
未決・気づいたこと: <あれば。無ければ「なし」>
書いた file: <path>
```

受け取った側は、spec_rev が今の BRIEF と同じかを確かめる。違えば古い前提の返事なので使わず、依頼し直す。結論だけで根拠の無い返事、「やりました」だけの返事も使わない。

## 5. 指摘と未決の台帳 (issues.md)

検品の指摘・ヒアリングで残った未決・作業中に分かった新しい事実を 1 か所に集める。消さずに状態を変える。

```markdown
| 番号 | 種類 | 内容 | 出どころ | 関係 | 状態 |
|---|---|---|---|---|---|
| I-01 | 指摘 | 3 枚目の割増率が台帳 L-04 の引用と違う | review/review-1.md #2 | B-07 | 済 (版 v3 で修正) |
| I-02 | 新事実 | 本人資料では対象を「全社員」としているが、原典は「週 20 時間以上」 | sources/S-03.md | B-07 | 本人待ち |
| I-03 | 未決 | 配布資料の部数 | ヒアリング 2 回目 | B-03 | 未決 (仮定 A-02 で進行) |
```

状態は「未決 / 本人待ち / 済 (根拠)」のどれか。「本人待ち」が残ったまま「完了」と言わない。

## 6. 作り手と点検役を分ける

- 自分の下書きを自分で点検した結果を「検品」と呼ばない (`review.md`)。
- 点検役には、正本の file と成果物だけを渡す。作り手の説明・会話・「ここは大丈夫」という申告は渡さない (先入観を移さないため)。
- 点検役の指摘に反対する時は、理由を issues.md に書いて残す。黙って無視しない。
- 直しの往復は既定で 2 巡まで。それで尽きなければ本人に返す。

## 7. 文脈を守る

モデルが一度に覚えていられる量は限られる。大事なことを押し出さないために:

- 過去資料・原典の全文を進行役の会話に流し込まない。量が多い読み取りは subagent に任せ、要点と短い引用だけを受け取る。
- 進行役が覚えておくのは: 本人の言葉、BRIEF の path と spec_rev、決定と理由、受け取った要点、未決。
- 取得した原典は `sources/` に抜き書きとして置き、必要な時にその file を読む。

## 8. 止まる時

- 機械チェックと検品が通ったら、報告して止まる。頼まれていない追加の点検の往復を始めない。
- 止める項目が埋まらない・本人の返事が要る時は、何が決まれば進めるかを書いて待つ。
- 中断する時は、issues.md と versions.md を最新にしてから止まる。再開した時は BRIEF.md → issues.md → versions.md の順に読み、「前回は <どこ> まで進んでいます。続きは <次のこと> です」と本人に伝えてから動く。

## 出典

- 正本の file を節目ごとに読み直す・依頼文と返事の決まった形・論点の台帳・作り手と点検役の分離・点検役に渡す物を絞る・直しは 2 巡まで: 提供者 (A&A) の社内の注意力設計 (attention engineering) をこの skill 向けに一般化
- 文脈なしに当てた修正はずれを生む、直す前に正本と元の入力を読み直す: BMAD-METHOD の Update mode (MIT)
- 承認の範囲は見せた物まで: obra/superpowers `brainstorming` (MIT)
- 答えを記録したら正本に反映し、矛盾を残さない: github/spec-kit `/clarify` (MIT)
