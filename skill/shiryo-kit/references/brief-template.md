# brief-template.md — BRIEF.md (資料要件の正本) の形

BRIEF.md は案件フォルダに 1 つ。以後の全工程 (骨子・下書き・台帳・検品・修正) はこれを読み直してから動く。
reviewer もこれを受け取るので、作り手の頭の中にしか無い前提を残さない。

## 書き方の決まり

- 要件には番号 (B-01, B-02, …) を振る。スライド・指摘・決定ログは番号で指す。番号は振り直さない (消す時は「取り下げ」と書いて残す)。
- 各要件に状態を付ける: **確定** (本人の言葉、または本人が「それで」と確認) / **仮定** (こちらの案を本人が了承) / **未確定** (値なし。理由と確定の条件を書く)。
- 本人の言葉は「」で逐語に残す。要約で置き換えない。
- 推測は書かない。書くなら「(推測)」を付け、要件にはしない。
- 空欄は空欄のまま残す。もっともらしい値で埋めない。
- 承認の前は `status: 下書き`・`spec_rev: 0`。承認前に本人が直した時も、決定ログに「変更」として本人の言葉で残し (spec_rev 0)、直した要約を読み上げ直して承認をもらう (`hearing.md` §要約の読み上げと承認)。承認で spec_rev 1 になる。
- 承認の後に変えてよいのは本人の言葉による時だけ。変えたら決定ログに追記し、spec_rev を 1 上げる。
- 顧問先の個人情報 (従業員の氏名・連絡先・健康情報など) は書かない。顧問先は呼び名 (例「A 社」) で書く。

## 雛形

```markdown
---
spec_rev: 1
status: 承認済み        # 下書き | 承認済み
案件: 20261018-就業規則セミナー
基準日: 2026-11-01     # 資料の内容が何日時点か
使う日: 2026-11-15
顧問先: なし           # 案件限定メモを読む相手の呼び名。無ければ「なし」
---

# BRIEF — <資料の呼び名>

## 承認記録
- <日時> 本人「<承認の言葉をそのまま>」 (spec_rev 1)

## 0. 三行
- 何の資料か:
- 誰に何をしてもらうか:
- 守ること:

| 番号 | 項目 | 内容 | 状態 | 根拠 |

| B-01 | 目的 | | 確定 | ヒアリング 1 回目「…」 |
| B-02 | 受け手 | §2 の persona | 確定 | |
| B-03 | 成果物 | スライド (pptx) + 読み原稿 | 確定 | |
| B-04 | 持ち帰らせたい行動 | | 仮定 | 本人了承 <日時> |
| B-05 | 場面 | 60 分・会場・投影 + PDF 配布 | 確定 | |
| B-06 | 基準日・使う日 | | 仮定 | |

## 2. 受け手 persona
- 呼び名:
- 受け取る場面:
- 受け取った後に決めること・すること:
- 知っていること・知らないこと:
- 刺さるもの・嫌うもの:
- 根拠:
- 未確定:

## 3. 場面と分量
- 時間・会場・人数・話す/配る:
- 枚数の目安 (モデルの案。本人が了承したら確定):

## 4. 入れること・言わないこと
- 必ず入れる:
- 触れない・言わない:
- 出さない固有名:

## 5. 使える資料 (P0 で読んだ物)
| file / URL | 何に使うか | 読めたか |
|---|---|---|

## 6. 口調
- 事務所共通: `資料メモ/事務所共通.md` の口調の節 (確認日)
- 今回だけの違い:
- reviewer 向けの要点 3 行 (語尾・呼びかけ・避ける言い方):

## 7. 仮定 (本人が了承済み)
- A-01 <仮定> — 了承 <日時>「…」

## 8. 未確定
- U-01 <論点> / 仮の扱い: <> / 確定の条件: <>

## 9. 環境と部品
- 質問 UI: あり / なし
- 別文脈の検品: subagent / 別プロセス / 使えない (→ 未検品)
- Web 取得: あり / なし
- 書き出し: build.py 可 / 不可 (理由)
- 描画部品: 既定 (HTML→pptx) / 他 (`adapters.md`)

## 10. ヒアリングの記録
### 1 回目 <日時>
- Q1 <問い> → 推奨: <> → 本人: 「<>」

## 11. 決定ログ (追記のみ。上の行を書き換えない)
| 日時 | 種類 | 内容 | 本人の言葉 | spec_rev |
|---|---|---|---|---|
| | 決定 | 初回承認 | 「…」 | 1 |
```

種類は次の 4 つ: **決定** (新しく決めた) / **変更** (確定を変えた。何から何へ) / **今回だけ** (メモと違う値を今回だけ使う。メモは書き換えない) / **仮定** (仮定を置いた・了承された)。

## 読み直しの合図

BRIEF.md の先頭の spec_rev を、subagent への依頼文と返事の両方に書かせる。返事の spec_rev が今の BRIEF と違ったら、その返事は古い前提で作られているので使わない (`attention.md`)。

## 出典

- 番号付き要件・状態の 3 区分・空欄を空欄で残す: 提供者の社内ブリーフ雛形を一般化
- 答えを記録して該当節に反映する・矛盾を残さない: github/spec-kit `/clarify` の Clarifications 記録 (MIT)
- 追記のみの決定ログ (決定・変更・上書き・仮定): BMAD-METHOD の `.memlog.md` (MIT, https://github.com/bmad-code-org/BMAD-METHOD)
