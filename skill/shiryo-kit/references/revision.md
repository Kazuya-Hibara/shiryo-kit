# revision.md — P7 修正 (直した後も正しさを保つ)

## 目的

本人が言葉で (または画面で指して) 直せるようにする。直した結果、確かめた事実や検品の結果が古くならないよう、変わった範囲に応じて前の工程に戻る。
どの版を検品し、どの版を渡したかを、いつでも示せるようにする。

## 1. 指示を受ける

- 会話の指示 (「3 枚目の 2 行目の数字が違う」)、画面で指した場所とコメント (`adapters.md` §3) のどちらでもよい。
- どこを指すか分からない時は、候補を 2〜3 個示して確かめる。これは場所の確認であって、新しい要件の質問ではない。
- 直す前に BRIEF.md を読み直す。指示が合意済みの要件を変えるもの (受け手・目的・成果物・時間・言わないこと) なら、決定ログに追記して spec_rev を上げてから直す。

## 2. 変更の種類と戻り先

変更が複数の種類にまたがる時は、一番重い行に従う。

| 変更の種類 | 例 | 戻る所 |
|---|---|---|
| 要件が変わる | 受け手が変わった、時間が 60 分→30 分、読み原稿も欲しい | P1 で該当項目だけ確かめる → BRIEF 更新 (spec_rev +1) → 影響する所を骨子 (P4a) から直す → P3 抜き出し直し → P6 → P5 (全体) |
| 主張・数字・日付・制度の内容 | 割合を直す、制度の説明を足す、期限を変える | P3: 原典を取り直し台帳を更新 → P4b → P6 → P5 (原典との一致を全体、他は該当枚) |
| 構成・順序・枚の追加と削除 | 2 枚を 1 枚に、事例を足す | 骨子 (タイトル列) で話が通るか確かめる → P3 抜き出し直し (新しい主張) → P6 → P5 (全体) |
| 言い回しだけ (主張・数字に触れない) | 語尾、言い換え、誤字 | 主張に触れていないことを確かめる (触れていたら上の行へ) → P6 → P5 (変わった枚と機械チェック) |
| 見た目・型 | 文字の大きさ、色、配置 | P6 → 描画の確認 (`check.py pptx`、はみ出し・重なり) → P5 (変わった枚と機械チェック) |

どの種類でも、`check.py deck` と `check.py ledger` は全体に対してやり直す (小さな直しが別の枚を壊すことがあるため)。

### 直した後に実行する順 (案件フォルダで。`<skill>` は skill フォルダ)

```
# 1. 主張・数字・構成・要件に触れた時だけ: 原典を取り直し、ledger.md と sources/ を更新 (evidence.md)
# 2. 機械チェック (全体)
python3 <skill>/scripts/check.py deck deck.html
python3 <skill>/scripts/check.py ledger ledger.md deck.html [ほかの成果物 ...]
# 3. 書き出しと描画の確認
python3 <skill>/scripts/build.py deck.html --out out
python3 <skill>/scripts/check.py pptx out/<名前>.pptx deck.html
# 4. 検品 (review.md の手順。新しい reviewer、渡すのは 3 つの path だけ)
python3 <skill>/scripts/check.py review-evidence review
# 5. 渡す前の照合
python3 <skill>/scripts/check.py manifest out review
```

5 が通らない (検品の後に直した・書き出し直した) のに渡す時は「未検品」として渡す。

画面で指して直してもらう時は `python3 <skill>/scripts/preview.py <案件フォルダ>` で表示し、直すたびに再読み込みしてもらう。終わったら `python3 <skill>/scripts/preview.py <案件フォルダ> --stop` で止める。

## 3. 数字を直してと言われた時

本人が「30% ではなく 25%」と言っても、そのまま書き換えて「確認済み」にしない。

1. 台帳の該当行と原典を見直す (取り直す)。
2. 原典が 25% → 直して、台帳の引用と確認日を更新する。
3. 原典が 30% のまま → 原典の該当箇所を見せ、「原典ではこう書かれています。どちらにしますか」と聞く (新しい事実による質問)。本人が 25% を選んだら、本人提供として残し、最後の報告に出す。
4. 確かめられない → [要確認] のまま 25% を書かない、または本人の希望で書く時は本人提供として残す。

## 4. 版の記録 (versions.md)

直すたび・書き出すたびに 1 行足す。sha256 は `python3 -c "import hashlib,sys;print(hashlib.sha256(open(sys.argv[1],'rb').read()).hexdigest())" <file>` で求める (どの OS でも動く)。

```markdown
| 版 | 日時 | 変わった所 | きっかけ | deck.html の sha256 | 書き出した file (sha256) | 検品 | 状態 |
|---|---|---|---|---|---|---|---|
| v1 | 10/18 21:10 | 初稿 | — | 3fa1… | out/deck.pptx (91c2…) | review-1: 直しが必要 | 作業中 |
| v2 | 10/18 21:40 | 3・5 枚目 (指摘 1,2) | review-1 | 77b0… | out/deck.pptx (a4d9…) | review-2: 合格 | 検品済み |
| v2 | 10/18 21:45 | — | 納品 | 77b0… | out/deck.pptx (a4d9…) | review-2 | 納品済み |
| v3 | 10/19 09:05 | 3 枚目の割合 | 本人の指示 | c018… | out/deck.pptx (5be3…) | review-3: 合格 | 検品済み |
```

状態は「作業中 / 検品済み / 検品済み・指摘が残っています / 未検品 / 納品済み」のどれか。

## 5. 渡す時の決まり

- 「検品済み」として渡せるのは、`check.py manifest out review` が通った時だけ (渡す file の sha256 が、検品した file の sha256 と一致する)。
- 通らない (検品の後に直した・書き出し直した) なら、もう一度検品するか、「未検品」として渡す (file 名に `_未検品`)。
- 渡す時の報告には、版の番号と検品の状態を書く: 「v3 をお渡しします。別の目で点検済みです (review-3)」。

## 6. 直しから口調を学ぶ

本人の言い回しの直しは口調の手がかりになる。同じ種類の直しが 2 回以上あったら、`資料メモ/事務所共通.md` の口調の節の更新案を作り、P8 で見せてから保存する。
