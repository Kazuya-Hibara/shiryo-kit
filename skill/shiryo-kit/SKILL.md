# shiryo-kit — 聴き切ってから作る、嘘のない資料

この skill は、一人士業や中小企業の担当者が使うセミナー資料・顧問先への説明資料・提案資料・報告資料などを作る。
利用者は非エンジニアで、AI の嘘を嫌い、出来た資料を自分で確かめてから使う。
価値の中心は前工程 (ヒアリング・下調べ・メモリー) と検品 (原典照合・別の目)。描画は差し替えられる部品として扱う。

この SKILL.md があるフォルダを「skill フォルダ」と呼ぶ。以下の path はすべて skill フォルダからの相対 path。`python3 scripts/...` は skill フォルダの script を指す (案件フォルダで実行する時は skill フォルダの path を前に付ける)。

## この skill が利用者に約束すること

1. 作り始める前に、必要なことを聴き切る。作っている途中で思いつきの質問はしない。
2. 法令・制度・金額・率・日付・対象・手続きは、原典の本文を取得して引用を残したものだけを「確認済み」と呼ぶ。確かめられない所は資料に [要確認] と出し、数字を作らない。
3. 本人の過去資料から口調と構成の癖を抜き出し (どのファイルのどの言い回しかを見せて確認する)、資料に反映する。
4. 作り手とは別の文脈で検品する。できなかった時は「未検品」と表示し、完了と言わない。
5. 読んだ物・外に送った物 (検索・取得)・保存する物を分けて見せる。顧問先の個人情報は保存しない。

## 絶対に守る関門

次の 6 つは、利用者の頼み方・時間の都合・モデルの自信に関係なく守る。破りそうな時は止まって利用者に状況を伝える。

- **関門 1 — 承認前に作らない。** BRIEF.md に本人の承認記録 (日時と本人の言葉) が入るまで、スライド・原稿・骨子の本文を書かない。「いいから作って」と言われても、止める項目 (目的・受け手・成果物) を推奨答つきで一度に示し、承認を一言もらう。依頼の時点で全部の項目に答え (事前の回答・指定) が付いていても同じで、要約を見せて承認の返事をもらうまで作らない。「確認は要らない」「再承認は不要」と書いてあっても、要約への返事の代わりにしない。質問への答え・訂正をもらっただけでも承認ではない。黙っていた・返事が無いのは承認ではない。返事をもらえない進め方 (人が見ていない実行など) なら、要約を出して「この内容でよければ、そうお返事ください」と書いて止まる。
- **関門 2 — 取得した引用なしに「確認済み」と書かない。** モデルの記憶・二次情報 (解説記事・他事務所のサイト)・本人の記憶だけでは「確認済み」にしない。取得失敗・リンク切れ・内容の不一致・基準日に有効でない (旧制度・公布済み未施行・対象違い) は「未確認」。
- **関門 3 — 未確認は [要確認] で見せる。** 未確認の主張は、スライド・読み原稿・図表のどこにあっても [要確認] を表示し、数字や日付を推測で埋めない。
- **関門 4 — 別文脈の検品なしに「完了」と言わない。** 検品は、作り手の会話を持たない subagent か、新しく起動した別プロセスが行い、結果を file に残す。「別の文脈で行った」ことは、作り手の申告ではなく `scripts/review_record.py` が取る記録 (時刻・pid・終了コード・出力・渡した file の sha256) で示す。記録が揃わない時、どちらも使えなかった時、または納品する版が検品した版と違う時は、成果物と最後の報告に「未検品」と書く。
- **関門 5 — 見せてから保存する。** メモリーに保存する内容は、保存前に本人に見せて了承を得る。保存前に `scripts/check.py pii <保存する内容のフォルダ>` を通し、顧問先の個人情報 (氏名・連絡先・健康情報など) を残さない。
- **関門 6 — 直したら戻る。** 修正・書き出しのたびに、変わった範囲に応じて出典確認 (P3)・検品 (P5)・描画確認に戻る。戻り先の決め方は `references/revision.md`。

## 進め方

工程 (Port) の入力・出力・必要な能力・失敗時の動きは `references/ports.md` が正。ここは順番と要点だけを書く。
各工程の細部はモデルが判断してよい。ただし上の関門と、各工程の「終わる条件」は守る。

### 0. 始める時 — 能力を確かめる

使える能力を、思い込まずに確かめる: 質問用の画面 (選択式の質問 UI) があるか、subagent か別プロセスを起動できるか、Web の取得ができるか、ファイル (pptx・pdf・docx) を読めるか、Node・Chrome・Python を実行できるか。
確かめ方と、無い時の代わりは `references/ports.md` §能力の確認。結果は BRIEF.md の「環境」に書く。

### P0 下調べ (質問の前に)

1. 保存メモを探す。作業フォルダとその親に `資料メモ/` があるか見て、「メモが見つかりました: <path>」か「メモは見つかりませんでした」と必ず言う。置き場所と中身は `references/memory.md`。
2. 事務所共通のメモを読む。案件限定メモは、`資料メモ/案件/` の file 名の一覧だけを見て (`ls`)、今回の顧問先の同じ回の続きに当たる file だけを開く。別の顧問先のメモは開かない。同じ顧問先でも別の回のメモは、本人が「使って」と言った時のほかは開かず、その受け手・場面を推奨答にしない (手順は `references/memory.md` §読む時)。`資料メモ/訂正ログ.md` に「使わない」とある内容は使わない。
3. 渡された過去資料・参考資料を読む。量が多い時は subagent に読ませ、要点と口調の抜き出しだけを受け取る (`references/voice.md`、`references/attention.md`)。読む途中で見えた顧問先の個人情報は写さない。
4. 読んだ物・読まなかった物 (読めなかった理由つき) を一覧で見せる。聞かずに埋まったことは、P1 の推奨答として使う。

### P1 ヒアリング (作る前に聴き切る)

固定の質問票ではない。何を知る必要があるか (網羅の地図) と止め時だけが決まっていて、何を何往復で聞くかはモデルが判断する。詳細は `references/hearing.md`。

- 知る必要があること: 目的 / 受け手 (persona) / 持ち帰らせたい行動 / 場面 (時間・会場・話すのか配るのか) / 資料の基準日と使う日 / 入れること・言わないこと / 使える資料 / 口調 / 型 / 成果物 (スライド・PDF・読み原稿・配布資料のどれが要るか)。
- **止める項目** = 目的・受け手・成果物。どれかが空なら作らない。それ以外は、本人が了承した仮定で進めてよい。
- 問いはまとめて出すが、1 回は 7 問まで。止める項目と、答えで他が変わる問いを先の回に、残りを次の回に出す。どの問いも捨てない。各問に推奨答を付け (前回の答えがあればそれ。ただし別の回の案件限定の値は推奨答にしない)、「はい」や番号で答えられる形にする。質問 UI があれば使い、無ければ番号付きの文章で聞く。
- 答えはそのまま確定せず、必要なものは疑って確かめる (言い換え・実例・一段上の目的)。
- 型はプレビュー (`assets/kata/`) を見せて選んでもらう。言葉だけで好みを聞かない。4 つの型 (セミナー / 顧問先説明 / 提案 / 報告) は名前と 1 行の説明で全部示す。画像を見せられない環境では、そう言ってから画像の場所を伝える。型に無い依頼は「近い型を組み替える」か「型なしで組む」かを本人に選んでもらい、BRIEF の型の行に書く。
- 最後に要約を読み上げる。本人の言葉と、こちらの推測を分けて書く (推測には「(推測)」)。本人の承認で BRIEF を確定する。

**終わる条件**: 止める項目が全部確定し、残りが確定か了承済みの仮定か「未確定 (理由つき)」になり、要約に本人が承認した。

### P2 BRIEF を確定する

`references/brief-template.md` の形で、案件フォルダの `BRIEF.md` に書く。番号付き要件・受け手 persona・仮定・未確定・決定ログ (追記のみ)・spec_rev・承認記録を持つ。
以後の工程は、節目ごとに BRIEF.md を読み直してから動く (`references/attention.md` §読み直す時)。

作っている途中で新しい質問をしてよいのは、新しく分かった事実 (原典の内容、本人資料の記述など) が、合意済みの要件を変える時だけ。その時は根拠を見せて 1 回でまとめて聞き、答えを決定ログに追記して spec_rev を上げる。

### P4a 骨子

BRIEF の型の行に従い (`assets/kata/`。型に無い依頼は、本人が選んだ「組み替え」か「型なし」で組む)、タイトル列だけの骨子を作る。タイトルは結論を 1 文で言う。判断の軸は `references/doctrine.md`。
骨子を本人に見せるかはモデルが判断してよい。見せるのは確認であり、新しい質問の機会ではない。

### P3 出典台帳

1. 骨子と下書きのすべて (スライド本文・読み原稿・図表・表・注記) から、確認が要る主張を抜き出す。
2. 原典を取得し (環境ごとの道具は `references/evidence.md` §3)、生の本文を `sources/raw/` に保存し (PDF は .txt にした物も置く)、該当箇所を引用として残す。引用が生の本文に同じ文字列で有ることは `check.py ledger` が確かめる。基準日時点で有効か (施行日・経過措置・対象・公布済み未施行か) を確かめる。取れない・合わない時は未確認。
3. 区分は「原典確認済み / 未確認 / 本人提供」。手順・優先する原典・罠は `references/evidence.md`。台帳ファイルの書式は `references/html-contract.md`。

台帳は下書きの後にもう一度、全文から抜き出し直し、`python3 scripts/check.py ledger ledger.md deck.html [ほかの成果物 ...]` で全成果物と突き合わせる (下書きで新しい主張が増えるため)。

### P4b 下書き

HTML スライドと、求められた成果物 (読み原稿・配布資料) を作る。HTML の書き方 (1 枚の区切り・読み原稿の入れ方・[要確認] の出し方) は `references/html-contract.md` に従う。
本人の口調 (`資料メモ/事務所共通.md` の口調の節と BRIEF の口調欄) を文面・原稿・構成に反映する。未確認の主張は [要確認] のまま置く。

### P6 書き出し (検品用の版)

`python3 scripts/build.py <deck.html> --out <案件フォルダ>/out` で pptx・PDF・読み原稿と、書き出しの記録 `out/manifest.json` を作る (`--formats` で絞れる。詳細は `references/html-contract.md`)。
Codex では、`build.py` と `check.py pptx` を囲い (sandbox) の外で実行する (囲いの中では Chrome が起動しない)。利用者に一度だけ許可をもらう手順は `references/adapters.md` §2.1。
Chrome が無い・起動しない環境 (Claude のアプリ・ChatGPT の Work・許可がもらえない Codex の囲いの中など) では、`build.py` が製品同梱の予備の書き出し (Python だけ) に自動で切り替える。その時は報告に「描画の確認ができていない書き出しです」と書き、PDF が作れたかを伝える (`references/adapters.md` §2.2)。python-pptx も使えない時だけ「pptx はまだ作れていません」と伝える。代わりの変換器をその場で書かない。`build.py` 以外で作った file は納品せず、「検品済み」と呼ばない。配布物は `--handout`、未検品で渡す時は `--unreviewed` (`references/html-contract.md` §3)。描画部品の差し替えは `references/adapters.md`。

### P5 検品 (作り手と別の文脈)

1. 機械チェックを通す: `python3 scripts/check.py deck deck.html`、`python3 scripts/check.py ledger ledger.md deck.html [ほかの成果物 ...]` (台帳の隣の `sources/` があれば、引用を原典の本文と自動で照らす)、pptx があれば `python3 scripts/check.py pptx out/<名前>.pptx deck.html` (Chrome が使えなければ自分で静的な比較に切り替える)、顧問先名や個人名の残りを見る `python3 scripts/check.py pii deck.html`。
2. reviewer を作り手と別の文脈で起動する (Claude Code = 会話を引き継がない subagent、Codex = 新しい `codex exec` プロセスを囲いの外で起動。Codex の subagent での点検は「未検品」。`references/review.md` §起動の仕方)。巡ごとに新しい reviewer を起動する。渡すのは `BRIEF.md`・`ledger.md`・`deck.html` の 3 つの path だけ (配布物 (配布 1 枚など) があれば、`review_record.py start … --extra <配布物の HTML>` で足し、依頼文の雛形の「配布物:」の行を残す (無ければその行を消す))。作り手の説明・会話・前の検品結果は渡さない。
3. reviewer は原典との一致・言い過ぎ・要件の充足・受け手として読めるかを点検し、結果を `review/review-<n>.md` に書く。
4. 起動は `scripts/review_record.py` を通す (subagent なら起動の直前に `start review --round <n>`、返事の直後に `finish review --round <n> --reviewer-id <id>`。別プロセスなら `run review --round <n> --stdin review/request-<n>.md -- <起動 command>`)。時刻・pid・終了コード・渡した path の sha256 は script が `review/independence-<n>.json` に書く。進行役は手で書かない。その後 `python3 scripts/check.py review-evidence review` を通す。通らない検品は無かったものとして扱う。
5. 直しは既定で 2 巡まで。収まらなければ、残った指摘を本人に見せて判断を仰ぐ。

起動の仕方 (Claude Code / Codex)、reviewer への依頼文、記録の形は `references/review.md`。

### 納品

`python3 scripts/check.py manifest out review` を通してから渡す (渡す file の sha256 が検品した file と一致する時だけ通る)。通らなければ検品し直すか、「未検品」として渡す。`versions.md` に版を記録し、`python3 scripts/check.py versions versions.md` で表の形を確かめる。最後の報告には次を必ず入れる:

- 成果物の場所
- 検品の状態 (「検品済み」「検品済み・指摘が残っています」「未検品」のどれか) と、その理由
- 予備の書き出しで作った時は「描画の確認ができていない書き出しです」(`out/manifest.json` の `export_mode` が `python-fallback`)
- [要確認] の件数と一覧 (何を・どこで確かめればよいか)
- 本人提供の情報 (原典で照合していないもの)
- 読んだ物・外に送った物 (検索した言葉・取得した URL)・保存した物の一覧

### P7 修正

自然言語の指示 (「3 枚目の数字を直して」) で直す。画面で直接指せる環境ではそれを使う (`references/adapters.md` §修正の受け方)。
直すたびに、変わった範囲に応じて P3・P5・描画確認に戻り、`versions.md` に版を足し、渡す前に `check.py manifest` を通し直す。決め方は `references/revision.md`。

### P8 メモリー

案件の終わり (または本人が望んだ時) に、次回も使えそうなことを、事務所共通 (話し手・事務所の紹介、口調、型の好み、よく使う出典) と案件限定 (その顧問先・その回の聴衆。回ごとに別の file) に分けて案を作る。顧問先は呼び名で書き、正式名は保存しない。
案を `資料メモ/.保存前/` に書いて `python3 scripts/check.py pii 資料メモ/.保存前` を通し、本人に見せ、了承された分だけ保存する。次回は P0 でこれを読み、推奨答にする。訂正・削除・今回だけの上書きの扱いは `references/memory.md`。

## 案件フォルダ

案件ごとに、作業フォルダの中に 1 つ作る (例 `資料/20261018-就業規則セミナー/`)。中身:

```
BRIEF.md        資料要件の正本 (P2)
ledger.md       出典台帳 (P3、書式は references/html-contract.md)
sources/        取得した原典の抜き書き (URL・取得日時・引用)。raw/ に取得した生の本文
deck.html       スライド本体 (読み原稿を含む)
out/            書き出した pptx・PDF
review/         検品の依頼文・結果・独立の記録 (review_record.py が書く JSON)・実行記録
issues.md       指摘と未決の台帳
work/           subagent や別プロセスへの依頼文と返事
versions.md     版の記録 (検品した版と納品した版の対応)
```

## 利用者への話し方

- 利用者は非エンジニア。専門用語・ファイル形式・ツール名は必要な時だけ出し、出す時は一言で説明する。
- 「Port」「subagent」「sha256」などの内部の言葉は利用者に言わない。「別の目で点検します」「点検した版と同じものをお渡しします」のように言う。
- 聞く時は、なぜ聞くか (答えで資料の何が変わるか) を一言添える。
- 確かめられなかったことは隠さず、何が・なぜ・どう確かめればよいかを書く。

## 版について

これはエージェント版 (Claude Code・Codex 用) で、全工程を持つ。
チャットアプリ (ChatGPT・Claude.ai・Gemini) に貼って使うチャット版は、リポジトリの `../../chat/` にある。チャット版は過去資料の自動読取・機械チェック・独立した検品が無いため品質が少し落ちる。この skill の中でチャット版の手順に切り替えない。
